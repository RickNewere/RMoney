# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the web/iPhone client of RMoney — a single static PWA (`index.html`, all CSS/JS inline, no build step) deployed to GitHub Pages at https://ricknewere.github.io/RMoney/ by `.github/workflows/deploy.yml` on every push to `main`. The repo must stay public: GitHub Free doesn't serve Pages from private repos.

Full system documentation (backend API, spreadsheet column logic, deployment gotchas) lives in the native-app project: `C:\Users\rober\Desktop\RMoney\CLAUDE.md`. Key points that apply here:

- The `API` constant and the `TABS` gid map at the top of `index.html` are duplicated in the native app's `config.js` — keep them in sync when the Apps Script URL or tabs change.
- **`api.json` must be updated with the same URL.** It is a two-line file, served by Pages alongside the page, whose only reader is the Android home screen widget. The widget is native code inside the APK, so it cannot read the `API` constant in this file, and a URL compiled into the APK would leave the widget dead after every "Nuova distribuzione" until someone rebuilds. Reading `api.json` at runtime is what keeps the widget alive across deployments — so a new Apps Script URL now means editing **two** things here, `index.html` and `api.json`.
- POST uses `Content-Type: text/plain;charset=utf-8` on purpose (avoids CORS preflight with Apps Script) — don't switch to `application/json`.
- UI is Italian. **The Android app is now a WebView shell loading this very page**, so this file is the single UI for both clients: a change here ships to Android too, with no APK rebuild.

## Structure of index.html

A top toggle (`#topToggle`) switches between two views. A third view, `#viewDettaglio`, has **no button**: it is reachable only by clicking a category in the summary, and the top toggle always closes it.

- `#viewInserisci` — the expense form (Persona, Conto, Data, Importo, Categoria, Nota, split checkbox) plus the "Debito condiviso" card.
- `#viewRiepilogo` — read-only summary, all from `?action=riep` (period + currency chosen in-app):
  - `#riepPeriodo` (Annuale/Mensile), `#riepValuta` (Euro/Franchi), `#riepAnno` / `#riepMese`.
  - `.ovTable` — Entrate/Uscite/Risparmio per Riccardo, Roberta and Combo. Uscite are derived client-side as `entrate - risparmio`; the backend only sends entrate + risparmio per person.
  - Three donuts (Roberta/Riccardo/Totale). Tooltips are **disabled on purpose**: the canvases are ~144px and CHF 5-digit tooltips overflowed the layout, so values are printed as text under each donut instead.
  - Bar chart, andamento line chart (annuale only), and the "Spese per categoria" section.
  - Chart **axis ticks carry no currency prefix** — adding `CHF ` made the labels overflow the card on phones. The symbol still appears in tooltips and in every text value via `riepFmt()`.
- `renderCategorie()` draws "Spese per categoria" and is driven by `#catChi` (Insieme/Riccardo/Roberta). It re-renders from `riepData` (the cached last response) **without refetching**, filters out zero rows, sorts descending, and stacks both people's bars in the Insieme view. Canvas height is set dynamically from the row count.
- `apriDettaglio(cat)` opens `#viewDettaglio`, listing the single expenses (date, note, amount, and who paid in the Insieme view) behind one category. It freezes category, currency and period into `detCtx` at click time and never re-reads the summary's globals afterwards — same snapshot rule as `caricaDebito()` below. `#detChi` then lets you switch person **inside** the detail without going back, and it is the only thing that changes: `caricaDettaglio()` refetches `?action=spese` with the `detReq` token so a slow response can't overwrite a newer one. Sanity check that must hold: Riccardo + Roberta always equals Insieme, both in total and in row count (verified live: 525,28 + 125,68 = 650,96 over 18 + 13 = 31 rows).
  - When the response carries no `spese` key the message names the backend version instead of saying "Nessun dato". That symptom means a cached page is still pointing at an older deployment, and the generic wording made it look like the category was empty.
  - The back button is `position: sticky` at the top of the view, outside the card: these lists get long and a button that scrolls away means scrolling all the way back up to leave.
  - **Deleting an expense lives here and only here** — deliberately not in the form or the summary. The `×` on a row POSTs `{op:'elimina'}`, which *empties* the sheet row instead of removing it (see the backend note): row numbers stay valid, so an open list never becomes a set of wrong addresses. The request carries the amount, note and category it expects to find, and the backend refuses if the row no longer matches — a stale list must not be able to wipe a different expense. After a delete, `detDirty` forces `caricaRiepilogo()` on the way back, otherwise the summary would still show the removed spend in its totals.
- `caricaRiepilogo()` guards against out-of-order responses with the `riepReq` token — rapidly switching period used to let a stale response win.
- **Measure from the browser, with exactly one tab of the app open.** Timings taken from Node miss the browser-cache fault above, and a second open tab silently competes for the same serialised queue: a POST measured at 20 s with three tabs open measured 2,8 s with one. Drive it by clicking the real controls and timing the `#msg` text, not by calling the fetch helpers.
- Web-app timings for a **shared** expense (from the page, one tab, click to "✓ Spesa aggiunta al foglio!"): LOG RICCARDO € 7,47 / 3,02 / 3,31 s, LOG ROBERTA € 3,29 s, LOG RICCARDO CHF 4,44 s, LOG ROBERTA CHF 6,05 s. Without the tick, LOG RICCARDO € 4,13 s. The debt card then refreshes 13-44 s in, behind the 4,5 s wait.
- `caricaDebito()` needs the **same** guard (`debitoReq`) plus something more: it snapshots `persona`/`conto` into locals when the request starts and renders only from those. Reading the globals in the `.then` was a real bug — switching tabs quickly showed one sheet's numbers under another sheet's labels and currency symbol, which is what made a user distrust the debt figure. For the same reason there is deliberately **no** `fmtImporto()`/`simbolo()`/`altraPersona()` helper here any more: any helper that reads the current globals re-creates the bug the moment someone calls it from a response handler. The "Saldato" button stays disabled until the figures on screen belong to the selected tab, so it can never be pressed against stale numbers.
  - **One request brings all four tabs** (`?action=debiti`), kept in the `fogliDebito` variable for the life of the page. `mostraDebito()` renders from it and `caricaDebito()` is the only thing that touches the network — called on load and after any write that changes ticks, **never** on a tab switch. Switching person or account used to fire a full backend round trip each time, which is what made "Roberta Euro" feel slow (the two euro sheets are 780 and 570 rows against ~110 for francs), and a switch made while the previous request was still in flight queued behind it. This is not a cache: the four totals come from a single read at a single instant, nothing is persisted, and a reload re-reads. `mostraDebito()` deliberately does **not** clear `#saldaMsg` — it also runs when the fetch completes, and would wipe the "Azzerate N spunte" result a moment after showing it.
  - **The debt is never read from a local copy.** There used to be a `rmoney_debito_<gid>` entry in localStorage per person/account combination, shown instantly and labelled "· ultimo noto", plus a background preload of the other three after the first successful read. Both are gone and must not come back. Once written, a combination was only refreshed when you actually looked at it, so every device carried the snapshot of its own last visit and the three disagreed: iPhone 359,23 against 360,23 in euro, Samsung 362,23 against 360,23. On a figure that decides who pays, a wrong number is worse than a slow one, so on a **cold** page the card shows `…` until the sheet answers, and `non caricato, tocca qui` if it doesn't. A one-off sweep deletes the leftover keys. The preload also fired three extra backend calls on first open, which fed the very slowness it was compensating for.
  - **Refreshing is not the same as having nothing**, and the two used to be conflated. `caricaDebito()` began by setting `fogliDebito = null`, so every refresh wiped the card back to `…`. The figure it wiped was correct and belonged to this session; the wipe just hid it for 8,5 s and, on a failed read, replaced it with `non caricato` — which is what "non si vede più il debito" was. Now the number stays on screen and a `#debtStato` marker next to the title says `aggiorno…` while a read is in flight, or `non aggiornato, tocca qui` (clickable) if that read failed. `…` and `non caricato` survive only for the cold case, where there genuinely is no number. The "Saldato" button is disabled while either marker is showing, so it can still never be pressed against a figure that is not the sheet's.
- **Never read the sheet immediately after writing to it.** A write leaves the workbook recalculating (SOMMARIO and the pivot read the LOG tabs) and the next read sits waiting for it. Measured after a shared expense on LOG RICCARDO, the same `?action=debiti`: **36,26 s** launched straight away, **4,29 s** four seconds later, **3,91 s** eight seconds later, while the write itself had taken 2,3 s. This is what made a shared expense feel broken — the save finished fast but the debt card sat on `…` for half a minute and then said "non caricato, riprova". `caricaDebito(ATTESA_RILETTURA_MS)` waits 4,5 s after any write. `?action=cerca` is exempt: measured at 2,12 s immediately after a write, so the lost-response check is never delayed.
- **A save can go two ways, and the fast one does not involve Apps Script at all.** `scriviDiretto()` talks to the Sheets REST API with an OAuth token: `values:batchGet` for headers plus tail, then one atomic `:batchUpdate` carrying `copyPaste` (format of a row born now), `setDataValidation` (the split checkbox), `updateCells` (the values) and the leftover clear. Measured live on LOG RICCARDO: **1474 ms** appending, **777 ms** with the tick, **708 ms** inserting a back-dated row that rewrote 9 rows. Against Apps Script, whose *startup alone* measured 1,0 s / 27,6 s / 3,0 s on three consecutive calls that never open the sheet.
  - **All four LOG tabs have the identical header row** `DATA | € or CHF | CATEGORIA | DETTAGLI | split`, with the tick in column 5, verified through `?action=debug` on each. The francs tabs are not a special case and the legacy `-` marker branch in `componiRiga` is dead in practice; keep it only as a guard. Tested live with the tick on all four: LOG ROBERTA row 567 in **2149 ms**, LOG RICCARDO CHF row 108 in **1781 ms**, LOG ROBERTA CHF row 112 in **1748 ms**, each landing as a real date, the right currency format copied from the first data row, and a genuine BOOLEAN `dataValidation` rather than the word TRUE. All test rows removed and a sweep of the four tails confirmed zero leftovers.
  - **The row is built to `gridProperties.columnCount`, not to `getLastColumn()`** as the backend does — 25 on every tab, against real content widths of 25/5/8/5. Writing empty `userEnteredValue` into the columns past the content is harmless because they are empty by definition, but it does mean the two paths write ranges of different widths; do not "fix" one to match the other without checking what lives out there first.
  - **`CODA_DA` is a copy of `SORT_FROM` and the copy is load-bearing.** 775 / 565 / 105 / 106, fixed on 27/07/2026. A first draft had 3 in there; that would have re-sorted two years of history on the first save. Never recompute or "simplify" these.
  - **The in-memory half of `aggiungiSpesa` is duplicated in the browser** (`calcolaScrittura`, `componiRiga`, `rigaVuota`, `dataRiga`, `trovaIntestazioni`). It has 38 offline tests; keep the two in step, because a divergence is a wrong row on the sheet two people settle up from.
  - **Dates cross as serial numbers, never as text.** Read with `UNFORMATTED_VALUE` + `SERIAL_NUMBER`, written back as `numberValue` at **noon** (`+0.5`), the same reason the backend uses `T12:00:00`: half a day of slack so no timezone can shift the calendar day. `updateCells` uses `fields: 'userEnteredValue'` so the cell's own number format survives.
  - **Google trims trailing empty cells from every row it returns.** Rows must be padded to the sheet's column count before the algorithm runs, or every column index after the first short row is off by however many cells were trimmed.
  - **The sign in is permanent, and getting there took two dead ends.** Google gives a browser-only app a one hour token and nothing else, so the first version made the user reconnect hourly. Two attempts to hide that failed and both are documented so nobody retries them: keeping the token in memory only meant every page reload threw away a still-valid hour (the iPhone home screen app reloads constantly), and refreshing it silently from the Aggiungi tap **does not work** even though the tap is a genuine user gesture — Google still wants to open a window, the promise never settles, and the 4 second cap that guarded it was pure added latency on top of an already slow Apps Script fallback.
  - **What works is the offline code flow.** `google.accounts.oauth2.initCodeClient` in popup mode returns an authorization code; Apps Script v35 exchanges it (`op: 'oauthScambia'`, `redirect_uri: 'postmessage'`) for an access token **plus a refresh token that does not expire**, and `op: 'oauthRinnova'` trades that refresh token for a fresh hour whenever needed. Confirmed live: forcing an expiry renewed the token in **56 s** with no window, no tap, and a genuinely different token valid for another 58 minutes, which then wrote to the sheet.
  - **The refresh token lives on the device, never on the backend, and that is a security decision not a convenience one.** Apps Script is only the custodian of the client secret (which cannot sit in a public repo) and stores nothing at all. The tempting version, where Apps Script holds the refresh token, would turn the public `/exec` URL into an endpoint that hands anyone an access token for **every** spreadsheet the owner has. Do not add any token storage to the backend.
  - **The renewal rides on Apps Script, so it inherits its flakiness and must retry.** Measured: one renewal came back after 22,7 s with an HTML page instead of JSON. The first version gave up silently at that point, which would have let the token expire anyway and thrown away the whole feature over one hiccup. `tentaRinnovo()` now backs off 20 s, 40 s, 80 s up to 5 minutes and never stops, and the renewal is scheduled **5 minutes before** expiry precisely to leave room for those retries. It stops only on `invalid_grant`, which means the consent was revoked — hence the backend must report the OAuth error *code*, not just `error_description`, because Google sends `{error: "invalid_grant", error_description: "Bad Request"}` and "Bad Request" alone is indistinguishable from a transient failure.
  - **The fallback is not optional.** The token lasts about an hour and cannot be refreshed silently in a way a browser will always allow, so any save without a valid token goes through Apps Script exactly as before. Roberta keeps working untouched until she connects. When the direct write *fails*, never fall straight through to Apps Script: check with `?action=cerca` first, or a request that actually landed gets written twice.
- **The write path and the debt are separate, and must stay separate.** They were entangled in two places and both cost the user time. The verification asked `?action=cerca&totali=1` so that one request could confirm the row *and* bring the four debt totals, and it was therefore delayed by `ATTESA_RILETTURA_MS` — the 4,5 s wait exists only because the **totals** need the workbook to finish recalculating, yet it was the confirmation of an already-written row that paid for it. Now `verificaSpesaScritta()` takes no `conTotali` argument, fires immediately, and the debt reads on its own schedule. Measured end to end on the real sheet: shared save confirmed in **2,8 s** (was ~7,3 s), plain save **2,4 s**, and the debt card never blanks. The backend still accepts `totali=1`; the web app no longer sends it.
  - **The new figure is arithmetic, not a guess.** Once the row is confirmed on the sheet, `aggiornaDebitoLocale(gid, importo)` adds `importo` to `totale`, `importo/2` to `meta` and 1 to `conteggio` — exactly what `_totaleCondivise` will compute on its next pass. Verified live: 558,08 → 558,12 locally after a € 0,07 shared expense, and the confirming read from the sheet returned the same 558,12 without changing the display. The read always overwrites the local figure when it lands, so the sheet has the last word. Do not extend this to deletes: the row's amount and tick state are not both known there, so those just refresh.
  - **The debt card has no error state at all, by requirement.** It went one attempt, then three, and both times running out of attempts put `non caricato, tocca qui` on screen, which names nothing broken: the next read almost always works. It now retries **indefinitely** with a growing pause (`PAUSE_DEBITO_MS` 2, 5, 10, 20, then 30 s, so a struggling backend is never hammered) and the card only ever shows `…` or the previous figure plus `ci mette più del solito, riprovo…`. The two stopping conditions are not failures and both resume by themselves: `navigator.onLine === false` shows `senza rete / riprovo appena torna` and restarts on the `online` event, and a hidden page suspends and restarts on `visibilitychange`. Tapping the card is now only a way to skip the remaining pause, not a requirement. Verified: 7 forced failures across 95 s never produced an error, and the chain then recovered on its own against a genuinely degraded backend, no tap involved. Do not reintroduce a bounded attempt count.
  - **A fixed retry count cannot work here, measured.** In a bad window, three of four single reads failed (16,3 s, 21,4 s and 50,6 s, each returning an HTML page instead of JSON) and the fourth answered in 3,1 s. Racing two requests against each other was tried and rejected: it rescued two rounds out of four and lost both others, while doubling the load on the thing that is already the scarce resource.
  - **The debt read retries; it used to have exactly one attempt.** The "no retries, ever" rule existed because an aborted fetch leaves the Apps Script execution running, so a retry piled on while a save was queued behind it. That reason died with the separation above: the save posts with `redirect: 'manual'` and confirms itself through `?action=cerca`, so an abandoned debt execution can no longer sit in front of anything the user is waiting for. `provaDebito(mio, ritardoMs)` drives the attempts, each with the 45 s ceiling, and stops early if `debitoReq` has moved on. With one attempt a single spike parked the card on `non caricato, tocca qui` for the rest of the session, which is exactly the iPhone screenshot that prompted this.
  - **The spike is Apps Script starting up, not the sheet and not the retrieval leg.** Measured six browser reads of `?action=debiti`: 45,0 s aborted at the ceiling, then 4,2 s ok, 38,3 s ok, 33,3 s ok, 35,1 s 404. Split into its two legs from Node, the retrieval leg is consistently healthy at **360-514 ms** (unlike writes, where it is the flaky one) while the execution leg is bimodal: **26,9 s and 27,0 s cold against 2,8-3,1 s warm**. And it is not the workbook: the same call with a nonexistent `action`, which never opens the spreadsheet, costs 1,0-2,5 s, so reading all four sheets accounts for only 0,3-2,6 s. Reading less would not help; there is nothing client-side to shorten, only to retry.
  - **Recovery must not depend on knowing where to tap.** The whole `#debt` card is the retry target (the "Saldato" button excluded, or pressing it would also fire a read), not the two words of grey text, and a `visibilitychange` back to `visible` retries automatically when the card is in error or stale. `mostraDebito()` shows `…` whenever a read is in flight **even if `fogliDebito` is still `'errore'`** — without that, tapping to retry changed nothing on screen and the card looked dead.
  - The Android widget is unaffected. `SPIA_SCRITTURE` in `App.js` only intercepts `action=debiti`, which is still what `caricaDebito()` calls. It actually gains: the post-write totals used to arrive on `cerca`, which the widget does not watch, so a shared expense never reached it until the next page load.
- **Every GET carries a `_=<timestamp>` and `cache: 'no-store'`.** Apps Script answers a 302 pointing at a **single-use** `user_content_key` on script.googleusercontent.com. A redirect replayed from the browser cache lands on a consumed key and returns a 404 HTML page, which surfaces as "non caricato" against a perfectly healthy backend. Seen live: `?action=debiti` 200 in 4,7 s, then the identical URL twice more, 404 and 404, while `?action=cerca` (a different URL) answered in 1,8 s. It does **not** reproduce from Node, which has no such cache — this is a browser-only fault, i.e. exactly where the users are.
- **Short timeouts were the biggest self-inflicted wound.** Because an abort leaves the execution running, every timeout adds a zombie holding the queue, and the recovery request then queues behind the zombie and times out too. Observed in one click: POST cut at 20,0 s, verification cut at 15,0 s, second verification cut at another 15,0 s — three zombies, fifty seconds burned, and the expense had been written by the first attempt. Ceilings are now deliberately generous (`TETTO_POST_MS` 45 s, verification 30 s, one attempt each) so a slow-but-healthy request simply finishes. In the normal case none of these numbers is ever reached: a save closes in 2,5-5 s.
- **Measured after all of the above**, writing *immediately* after switching tab, one request per save, no verification message on any of them: LOG RICCARDO € 3,01 s / 28,08 s (tick), LOG ROBERTA € 12,09 s / 4,09 s, LOG RICCARDO CHF 4,42 s / 5,16 s, LOG ROBERTA CHF 3,33 s / 2,48 s. Six of eight between 2,5 and 5,2 s. The two outliers are not the script (`ms` reports 1-2 s inside `aggiungiSpesa`) — they are Apps Script's dispatch plus the workbook recalculating, neither of which the client can influence. Do not chase them with client-side changes; the levers left are all in the spreadsheet's own formulas.
- **The save does not follow Apps Script's redirect.** `apiPostSenzaRitorno` posts with `redirect: 'manual'` and stops at the 302; `apiPost` (which does follow) is kept only for settle/undo/delete, where the body is actually needed. A `/exec` call is two legs — the script running, then fetching the result from script.googleusercontent.com — and measurements showed the first leg is consistently ~3 s while the **second** stalls for 12-42 s and then returns an HTML error page. One stall even returned `doGet`'s output to a POST. That leg is pure waste for a write: when Apps Script answers with the redirect, the row is already on the sheet. Following it, roughly one save in four came back unreadable; not following it, sixteen out of sixteen succeeded. Confirmation comes from `?action=cerca` straight after, and the success message is shown as soon as the POST leg returns, then corrected if the check says the row is not there.
- **What is left is Apps Script's dispatch**, 8-11 s on about three writes in twenty, measured as the gap between sending and `doPost` starting. No client change touches it. See the RMoney CLAUDE.md for the full four-way breakdown and the list of causes already measured and ruled out.
- **Aborting a fetch does not cancel the Apps Script execution.** The abandoned request keeps holding the queue, so a retry stacks behind work that is still running: a short ceiling makes things slower, not faster. Measured: first read cut off at 20,0 s, retry 36,5 s then 404. `TETTI_MS` is therefore `[45000, 45000]` — generous, so a healthy-but-slow read is never cut off, with one retry left for a genuinely lost response. A read that legitimately took **20,5 s** completed and rendered under this setting; under the old 20 s ceiling it would have been killed.
- **Request count is the thing to watch, not payload size.** Apps Script does **not** serialise an owner's executions (measured: a write finished in 4,65 s while a parallel read was still running at 16,39 s — an earlier claim to the contrary in this file was wrong), but every extra request is another chance to draw a slow dispatch, and aborting a fetch does not cancel the execution, so a short ceiling plus a retry adds load instead of relieving it. Hence: categories are fetched once per sheet per session (`catLetti`) instead of on every tab switch; a tab switch fires no debt request at all; and the ceilings are generous rather than tight (`TETTO_POST_MS` and `TETTI_MS` 45 s, verification 30 s, one attempt each).
- `verificaSpesaScritta()` asks `?action=cerca` — one attempt, 30 s ceiling — and nothing else. A lost response nearly always means the expense **was** written — the script side takes 1-2 s and it is Google's retrieval leg that fails — so this path runs often and must be fast and near-certain. It used to call `?action=spese`, the heaviest endpoint, which frequently failed and produced "non riesco a verificare" for expenses that existed. The user-facing wording is "Verifico sul foglio…", not "Risposta non valida": the latter described a save failure that had usually not happened. **Never turn a lost response into a retried POST** — that is how a duplicate row gets written.
- If the `salda` POST fails at the network level, the handler re-queries `?action=debito` and reports whether the sheet was actually cleared. "Errore di rete" alone left the user unable to tell whether the write had landed.
- No PIN/auth: considered and explicitly rejected by the owner.
- Icons (apple-touch-icon.png, icon-192/512.png, favicon.png) are generated by `RMoney\backend\make_icon.py` — regenerate there, don't hand-edit.
