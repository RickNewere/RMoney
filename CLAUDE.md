## Architecture

Backend = a Google Apps Script Web App bound to the spreadsheet (`backend/Codice.gs`). Clients talk to it over HTTPS:

- `GET  {API_URL}?action=categorie&gid=...` → `{ok, version, categorie:[...]}` — distinct values actually used in the CATEGORIA column of that tab, sorted.
- `POST {API_URL}` body `{gid, data:"YYYY-MM-DD", spesa, categoria, nota, segno}` → appends a row.
- `GET  {API_URL}?action=riep&conto=Euro|Franchi&tipo=annuale|mensile&anno=YYYY[&mese=M]` → `{ok, version, riepilogo:{...}}`. Read-only. Recomputes the summary from the two LOG sheets of the currency for an arbitrary period (a month or a full year), so the web "Riepilogo" section can pick any month/year. Same shape as `riepilogo` (overview/entrate/risparmio/spese per person + andamento for annuale). Classification mirrors the SOMMARIO sheets: a row is a **spesa** iff its category is one of the 15 in `SPESE_CATS`; everything else (stipendi, tredicesime/quattordicesime, and **storni e rimborsi**) counts as **entrata**; `risparmio = entrate - spese`. Validated against SOMMARIO ANNUALE 2025 (entrate exact; spese within ~7€ due to minor LOG-vs-sheet category quirks). This is what the web app uses now; the older `?action=riepilogo&gid=` (reads a fixed SOMMARIO sheet) is kept but unused.
- `GET  {API_URL}?action=riepilogo&gid=<gid di un foglio SOMMARIO>` → `{ok, version, riepilogo:{...}}`. Read-only. Reads a SOMMARIO sheet (ANNUALE/MENSILE × euro/CHF) and returns `overview` (entrate/uscite/totale + `periodo`), `entrate` and `risparmio` per person (roberta/riccardo/totale), and `spese.roberta`/`spese.riccardo` as `[{categoria, importo}]`. For ANNUALE sheets it also returns `andamento` (monthly savings series roberta/riccardo/totale) read from the hidden pivot sheet. The 4 SOMMARIO gids: annuale euro `738641296`, annuale CHF `637629592`, mensile euro `282752746`, mensile CHF `387921258`. Values come from `getValues()` (the accounting "-" is numeric 0); anchors ("OVERVIEW", "ENTRATE", "RISPARMIO", "SPESE ROBERTA/RICCARDO") are matched by text so the extraction survives row shifts.
- `GET  {API_URL}?action=debito&gid=X&gidPartner=Y` → `{ok, version, debito:{mio:{totale,meta,conteggio}, partner:{...}, netto}}`. Read-only. Sums the amounts of rows marked with a dash `-` (shared expenses split 50/50); `meta`=totale/2. `netto = mio.meta - partner.meta` is the per-currency settlement between the two same-currency tabs (>0 ⇒ partner person owes the tab's person). `gidPartner` is optional. This never writes to the sheet.
- `GET  {API_URL}?action=condivise&gid=X` → `{ok, version, condivise:{tab, righe:[{riga, data, importo, categoria, nota, split}], totale, meta}}`. Read-only (v17). Itemises the rows the debt calculation sums, with their **sheet row number**, using exactly the same criteria as `_totaleCondivise`. This exists to reconcile the debt by hand: a mismatch is normally one forgotten row, and this turns "the total looks wrong" into "row 758, bennet, 12,51" in one call.
- `GET  {API_URL}?action=spese&conto=Euro|Franchi&tipo=annuale|mensile&anno=YYYY[&mese=M]&persona=Riccardo|Roberta|Insieme&categoria=<nome>` → `{ok, version, spese:{categoria, persona, valuta, periodo, righe:[{data, ts, importo, nota, persona, riga}], totale, conteggio}}`. Read-only (v18). The drill-down behind the web summary: `?action=riep` gives per-category totals, this gives the single expenses making up one of those totals, newest first. It filters the same LOG rows with the same period logic as `getRiepCalc`, so the sum of `righe` always matches the category total shown in the summary — if it ever doesn't, the two filters have drifted apart.
- Debug endpoints: `?action=debug&gid=` (tab name, row/col counts, first rows, last row) and `?action=catdebug&gid=`.

Tab routing: the four spreadsheet tabs are selected by Persona+Conto via gid — Riccardo Euro `113020932`, Roberta Euro `1888286288`, Riccardo Franchi `650699013`, Roberta Franchi `1063479927`. The map is duplicated in `config.js` (native) and in `RMoney-web/index.html` (web); change both.

Backend column handling (important — the sheets are not plain tables):

- Row 1 of each tab is a title; real headers are on row 2. `_findHeader()` scans the first 8 rows and scores keyword matches to find the header row. Never assume row 1.
- Columns are matched by substring on header names (`_colFor`): amount matches €/chf/importo/…, note matches dettagl/nota/…
- Date cell gets number format `d mmm yyyy` (renders "20 lug 2026" with the sheet's Italian locale) — no time.
- Shared expenses are marked in a dedicated **`split`** column (header `split`, real Sheets checkbox) placed immediately to the RIGHT of the note column. A row is shared if that cell is boolean `true` (or the legacy `-`, still recognized for backward compat). When `segno:true`, `aggiungiSpesa` inserts the row, then on the split cell calls `insertCheckboxes()` and `setValue(true)` — the checkbox must be applied AFTER `appendRow`, otherwise a bare `true` on a cell without checkbox validation renders as the literal text "true" (this was a real bug). If the `split` header is absent it falls back to writing `-` at note+1. `saldaFoglio` likewise re-applies `insertCheckboxes()` after clearing, so it never leaves the text "false" on cells lacking validation.
- **`appendRow` does not apply formatting** — it only inherits what already exists in the destination row. The tabs carry an accounting currency format (` € 9,50 `, ` CHF 22,70 `) applied to a *finite* range, so once the data outgrows that range new rows are born unformatted and an amount shows as `1` instead of ` € 1,00 `. This actually happened on LOG RICCARDO at row 770 and is why inserts "stopped working" after months of being fine. Since v15 `aggiungiSpesa` copies formats onto the new row with `copyTo(..., PASTE_FORMAT)` before re-applying the date format. The model row is the **first data row** (`h.row + 1`), deliberately not `r - 1`: when the last rows are already broken, copying from them propagates the defect. The same reasoning applies to the `split` checkbox: it is inserted on **every** row, shared or not, so a plain row is an unchecked box rather than an empty cell.
- `sistemaFormatoRighe(gid, daRiga, aRiga)` repairs rows written before that fix, by hand from the Apps Script editor. It writes **formatting and checkboxes only** and preserves existing ticks: dates, amounts, categories and notes are never touched. **The one real case (LOG RICCARDO, rows 770-774) is already sorted — the owner fixed it. Do not suggest running `sistemaRigheRotteRiccardoEuro()` again;** it is kept only as a template should the same breakage reappear elsewhere.
- One-time setup: `setupSplitColumn()` (run manually from the Apps Script editor) adds the `split` header + checkboxes to the 4 known tabs and converts existing `-` marks to checked. Touches only that single column.
- The spreadsheet has a **hidden sheet** "Tabelle brutte che nessuno vuole vedere" (gid `1943088578`, constant `GID_PIVOT`) holding the source pivots for the SOMMARIO charts, including the monthly "Andamento Risparmi" series (euro table first, CHF table second). `?action=riepilogo` reads the andamento from here.
- **Tail-only date sorting (v20).** `SORT_FROM` maps each LOG gid to the first row the app is allowed to reorder, frozen on 27/07/2026 at that sheet's then-last row + 1 (Riccardo € 775, Roberta € 565, Riccardo CHF 105, Roberta CHF 106). `_ordinaCoda()` sorts only from there down, after every insert and after any delete inside that zone. Everything above the threshold is never read or moved: the history keeps whatever order it already had, which is **not** chronological (a sample of 122 rows had 9 date inversions), so the sheet as a whole will never become fully sorted — that was the accepted trade-off for not disturbing existing rows. Do not recompute these thresholds: raising them abandons rows already being sorted, lowering them reshuffles the frozen history.
  - Blank cells sort to the bottom, so the hole left by a delete drifts to the end of the zone on its own and the space becomes reusable. `_primaRigaLibera()` additionally lets `aggiungiSpesa` fill a blank row in the zone instead of always appending.
  - **An emptied row must be left with NO checkbox (v21).** Up to v20 `svuotaRiga` kept an unchecked box on the cleared row, reasoning that reuse needed the validation in place. The owner rejected that: a grey box on a row with no expense reads as a leftover. It also had a concrete cost, since a boolean counts as content, so `getLastRow()` never shrank and the sheets over-reported their length (LOG RICCARDO said 777 rows against a real 774). Keeping the box was never actually necessary: `aggiungiSpesa` calls `insertCheckboxes()` on the destination row on every write, whether it appends or reuses a blank. So `svuotaRiga` now does `removeCheckboxes()` + `clearContent()` on the split cell.
  - Sorting moves values, so the split column has to be rebuilt afterwards, and it needs **two opposite passes** — this is `_sistemaCheckboxCoda()`, shared by `_ordinaCoda` and the one-off cleanup. Rows that still hold a expense get `insertCheckboxes()` and their boolean written back, otherwise a moved cell can end up showing the literal text "true". Rows that are empty get `removeCheckboxes()`, otherwise the sort would silently re-create exactly the residue v21 removes. Order matters: `removeCheckboxes()` also wipes the cell value, so the ticks must be read out of the range **before** touching the column. The split of full rows from empty ones relies on blanks sorting to the bottom, so the function only needs the index of the last non-empty row.
  - `pulisciCheckboxVuote()` is a one-off for the residue left by ≤v20 deletes: it runs `_sistemaCheckboxCoda` over the tail of all four sheets, then `_togliCodaVuota()`. Run once from the Apps Script editor — note that runs the **saved** code, so no redeploy is needed for it. Afterwards it has no further purpose, since a normal insert or delete cleans that sheet's tail anyway.
  - `_togliCodaVuota()` exists because not every stray checkbox came from a delete. `sistemaFormatoRighe` applies the box across a whole row range, blank rows included, so the manual repairs left blank-but-checkboxed rows **below** `SORT_FROM`, in the frozen zone the sorter never touches (confirmed on LOG RICCARDO row 774). It strips the box only from **trailing** blank rows and stops at the first row holding a real expense, so the history is never rewritten; it also bails if `getLastRow()` fails to shrink, which means some other column is keeping that row alive.
  - Consequence for clients: a sort invalidates the row numbers held by an open `?action=spese` list. The `atteso` guard on delete is what keeps that safe — it refuses rather than deleting whatever now sits at that row number.
- `POST {op:'elimina', gid, riga, atteso:{importo, nota, categoria}}` → `svuotaRiga()` (v19). Clears date/amount/category/note on that ONE row with `clearContent()` so formatting survives, and since v21 removes the split checkbox entirely rather than leaving it unchecked. It deliberately **does not delete the row**: removing it would shift everything below and invalidate every row number already handed to the client by `?action=spese`. `atteso` is a guard, not decoration — the row is only cleared if it still holds the amount, note and category the user was looking at, so a stale list cannot wipe the wrong expense. Reachable in the UI only from the category detail view.
- `POST {op:'salda', gid}` → `saldaFoglio(gid)` unchecks every `split` cell of that ONE tab (write limited strictly to the split column; expenses are left intact). Backs the in-app "Saldato · azzera split" button, which confirms before firing.
- `POST {op:'annullaSalda', gid}` → `annullaSalda(gid)` puts back exactly the ticks the last settle removed (v22). **This exists because the settle used to be irreversible and 29 ticks were lost on LOG RICCARDO.** Since v22 `saldaFoglio` records the affected row numbers in `PropertiesService` before clearing; the undo re-ticks them and then **consumes** the record, deliberately — undoing twice, or much later, would re-tick rows that may have changed meanwhile. The web client shows an "↩ Annulla" button after a successful settle, and the confirm dialog now states the amount at stake instead of a generic "are you sure".
- **The undo is not retroactive.** Ticks cleared by a pre-v22 deployment left no record, so nothing can restore them from the script. For that case there is `ripristinaSplitDaCopia(idCopia [, nomeTab])`, run by hand from the editor: the owner makes a *copy* of an older revision via File → Cronologia versioni → three dots → "Crea una copia", and the function reads the `split` column out of that copy and re-applies it. It pairs sheets **by name** (a copy has its own gids), touches only the split column, and is **additive** — it never clears a tick, so expenses and ticks added since the copy survive. This is how the 29 rows were actually recovered; verified afterwards against the known figures (29 rows, 1068.67, net -362.23) with the August expenses still intact.

CORS: Apps Script `/exec` sends `Access-Control-Allow-Origin: *`. The web client POSTs with `Content-Type: text/plain;charset=utf-8` to avoid a preflight — don't change it to `application/json`.

## Backend deployment (manual, no CLI)

`backend/Codice.gs` is source only — it runs inside the sheet's Apps Script editor (Estensioni → Apps Script), where the user pastes it. To ship a change **without changing the URL**: Distribuisci → Gestisci distribuzioni → ✏️ → Nuova versione. A "Nuova distribuzione" creates a NEW `/exec` URL and breaks both clients (this happened repeatedly; the URL then has to be updated in `config.js` AND `RMoney-web/index.html`).

The `VERSION` constant in Codice.gs is a deliberate marker: bump it and check any endpoint's `version` field to verify what's actually live. Local Codice.gs is **v22** (the settle operation is reversible, plus `ripristinaSplitDaCopia`) and is live, earlier **v21** (a deleted row leaves no checkbox behind), **v20** (tail-only date sorting + blank-row reuse), **v19** (`{op:'elimina'}`), **v18** (`?action=spese`, the per-category drill-down), **v16** (v15/v16: new rows copy their formatting from the **first data row** and always get a split checkbox, plus `sistemaFormatoRighe(gid, da, a)` to repair rows written before the fix; the formatting bug is closed — the fix is live and the affected rows have been repaired), earlier **v12** (v10: split cell gets a real checkbox via `insertCheckboxes()`+`setValue(true)` after `appendRow` instead of a bare `true` that rendered as text; v12: adds `action=riepilogo`); a redeploy is required for it to take effect. v7's only addition (serving `backend/App.html` on plain GET) was superseded by the GitHub Pages client; `backend/App.html` is dead code kept for reference.

Current live URL (answers **v22**): `https://script.google.com/macros/s/AKfycbxGR7ekEWGJGxstAMBBOpBvzTHVTmD21WbkJG3rWeekaIoYCVujUNuhhFYQyrSK0yH_mw/exec`.

**A new URL means editing THREE files, not two:** `RMoney-web/index.html` (the `API` constant), `RMoney-web/api.json` (read at runtime by the Android widget), and `config.js`. Miss `api.json` and the app works while the widget silently keeps talking to the archived deployment.

At least five older deployments are still live and answering (v17 `AKfycbzH9jpm…`, v18 `AKfycbyT4YZ…`, v19 `AKfycbyVsbG2…`, v20 `AKfycbw4Bsnd…`, v21 `AKfycbzXHWg…`); they should be archived. Every one was created by choosing "Nuova distribuzione" instead of "Nuova versione", and the symptom was always the same: the code looks deployed but the clients keep talking to the old URL.

**Apps Script is the capacity bottleneck, and it degrades before it fails.** Measured under load on the free tier: the same `?action=categorie` call took 2.7 s, then 19.6 s, then 33.5 s, the last two returning an **HTML page instead of JSON** with HTTP 200. Two minutes of quiet and it was back to 6.9 s and correct data. So it is congestion, not an exhausted daily quota, and the client's job is to ask less and to survive a non-JSON answer rather than to retry harder. Every widget refresh costs three requests, which is why the refresh cadence is deliberately conservative (see the widget section).

## Android home screen widget

Two widgets: **"Debito"** (2x2, shared balance per currency) and **"Riepilogo"** (full width, the same balance plus a donut of the month's income/spending/savings). They are the one part of the Android app that is NOT the WebView, and that is not a choice: an Android widget is drawn by the launcher process from `RemoteViews`, so it cannot host a WebView or run the web app. Built with `react-native-android-widget` (v0.21, Expo config plugin). Expo's own `expo-widgets` is iOS only, which is also why the iPhone client, being a home screen web app, can never have one.

Files, and which layer each belongs to:

| file | role |
|---|---|
| `index.js` | entry point: registers the app, the widget task handler and (by importing it) the periodic task |
| `App.js` | WebView shell + the write-spy injection + the refresh triggers |
| `widgets/aggiorna.js` | the only place that calls `requestWidgetUpdate`; throttling, coalescing, two-phase draw |
| `widgets/attivitaPeriodica.js` | the WorkManager periodic job |
| `widgets/disegna.js` | composes either widget; single source of truth for the trees |
| `widgets/debitoData.js` | debt fetch, retries, cache, `formattaImporto` |
| `widgets/riepilogoData.js` | monthly summary fetch (**francs**, see below) |
| `widgets/tortaSvg.js` | donut geometry as an SVG string for `SvgWidget` |
| `widgetTaskHandler.js` | headless dispatch for system-initiated updates |

- **The donut reads the FRANCS sheet, and that is deliberate.** Salaries land on the CHF account, so the euro sheet has `entrate: 0` in every month and a euro donut would forever read "all spending, negative savings". July francs: income 8720.60, spending 1881.53, savings 6839.07. Two slices, not three: savings is already income minus spending, so a third slice would count income twice — the ring *is* the income. If income is 0 or spending exceeds it there is no share to draw, and the ring goes solid red instead of inventing a proportion. If the current month has no movements yet (typical on the 1st) it falls back to the previous month, and the label always names the month shown.

- **`package.json` `main` is `index.js`, not `expo/AppEntry.js`.** The widget handler has to be registered next to `registerRootComponent`, and the default Expo entry point only does the latter. Reverting `main` silently disables the widget: the app still runs, the widget just never draws.
- The widget declaration lives in `app.json` under `plugins`. `expo prebuild` turns it into `android/app/src/main/res/xml/widgetprovider_debito.xml`, a `<receiver android:name=".widget.Debito">` in the manifest, and a generated `widget/Debito.java` extending `RNWidgetProvider`. All of that is regenerated, so never hand-edit it — change `app.json` and prebuild.
- **The backend URL is resolved at runtime** from `https://ricknewere.github.io/RMoney/api.json`, with `config.js`'s `API_URL` as fallback. This exists because the Apps Script URL changes on every "Nuova distribuzione" (five times in a single day of work at one point) and a URL compiled into the APK would leave the widget dead until someone rebuilt it. That JSON file lives in the `RMoney-web` repo and has to be updated together with `index.html`.
- `leggiDebito()` never rejects. On any failure it falls back to the last value cached in AsyncStorage, flagged `vecchio`, because a widget showing a stale number beats one showing nothing. If there is no cache either it returns empty and the widget invites a tap.
- **Never let two backend reads overlap, and never parallelise them.** This cost hours. Apps Script serialises requests from the same user, so concurrent calls do not run concurrently: the second one sits in a queue while its own abort timer runs, and dies with `Aborted`. A `Promise.all` over the two currencies (written as an "optimisation") made the second currency fail on every attempt, and because one failure discarded the whole result the widget silently kept redrawing the same stale numbers for hours. Measured on the live backend: euro ~3 s, francs ~10 s alone, **16 s when fired together**. Two rules follow, both enforced in code: the currencies are read **one after the other**, and `leggiDebito()`/`aggiornaWidget()` each keep a single in-flight promise so that the five triggers (app start, app exit, periodic job, widget tap, the wide widget wanting the same data) share one read instead of racing. Verified: with the guard, three simultaneous callers produce exactly one real execution.
- **`TIMEOUT_MS` must stay well above the slowest single call.** It was 12 s while the francs call alone takes ~10 s — a fuse waiting to blow even without the parallelism bug. Now 25 s with 2 attempts.
- **A failure on one currency must not discard the other.** It used to, which is why a fresh euro figure was thrown away because francs had timed out. Each currency now falls back to its own cached value.
- **`requestWidgetUpdate` resolving means nothing.** The library resolves as soon as it has *launched* the draws — internally a `forEach` with an async callback — so a failure inside becomes an unhandled rejection and vanishes. The app logged "widget aggiornato" for hours while the widget on the home screen never changed. Any log that claims success must come from **inside** `renderWidget` (see the `disegno` / `disegno pronto` / `disegno FALLITO` traces), never from the outer promise. When debugging this widget, the only trustworthy evidence is the clock drawn in its own corner.
- **`updatePeriodMillis` is not the periodic refresh; WorkManager is.** The widget alarm fires (`dumpsys alarm` showed it at 18:54, 19:29, 19:43) while the widget stayed frozen for eight hours, which matches the API contract: best effort, the device is never woken for it, OEM power management delays it further. The real periodic refresh is `expo-background-task` (WorkManager) in `widgets/attivitaPeriodica.js`, at **30 minutes**. It is the only mechanism that can pick up an expense entered from the *other* person's phone, because Apps Script cannot push to a device.
- **Never call `registerTaskAsync` unconditionally at startup.** Re-registering a live periodic job REPLACES it and restarts its countdown from zero. The call sat in an app-start effect, and since the owner opened the app precisely to check whether the widget had refreshed, every check pushed the next run 30 minutes away — it could never fire. Guarded now with `TaskManager.isTaskRegisteredAsync`; the log says `lavoro periodico gia' attivo, non lo tocco` on later launches, and that line is the proof the timer was left alone.
- **Refresh triggers, and the throttle between them.** `App.js` injects a script that wraps `window.fetch` in the WebView and posts `foglio-cambiato` on any successful POST to `/exec` — so adding, deleting and settling all refresh the widget within seconds. Plus app start, app exit, and the periodic job. `DISTANZA_MIN_MS` (10 min) suppresses *spontaneous* repeats, because opening and closing the app fired two reads seconds apart and that alone was enough to congest Apps Script. `SEMPRE` lists the reasons that bypass it: a sheet write, a widget tap, and **app start** — opening the app is a deliberate gesture, and throttling it made the widget stale exactly when it was being looked at.
- **Draw from cache first, then from the network.** After every reinstall Android resets the widget to its blank initial layout; with the backend taking 10-30 s the read rarely finished before the app went to background, so the widget stayed empty. `aggiornaOra` now draws immediately from the AsyncStorage cache and redraws when fresh data lands. The log distinguishes the passes as `(motivo/cache)` and `(motivo/rete)`.
- **Limit worth stating plainly:** the write-spy only catches changes made on *this* phone. A change made from the iPhone cannot arrive before the periodic refresh, a tap, or an app open.
- **Reinstalling the APK removes the widget from the home screen.** Observed, not theorised: `dumpsys appwidget` logged a `cancel` of the provider seconds after `adb install -r`, and the placed instance was gone. The provider itself re-registers fine, so the fix is simply to add the widget again by hand. Expect this after every rebuild and warn the owner rather than debugging a "widget disappeared" report. `dumpsys appwidget | grep -A2 rmoney` shows both the registered provider and the live instances, and its `min=(WxH)` is width and height in dp packed as `dp*256+1`, so 200x80dp reads as `51201x20481`.
- **Amounts are formatted by hand, and the rule is not the obvious one.** Italian CLDR sets `minimumGroupingDigits=2`, so `toLocaleString('it-IT')` prints `1165,86` with no separator and only starts grouping at `10.000,00`. The widget cannot call `toLocaleString` (headless task, full Intl not guaranteed), so `formattaImporto` reproduces that rule with an explicit `length >= 5` check. A "nicer" formatter that groups from 1.000 was written first and made the same number read differently in the widget and in the app. Verified: both agree on 13 values across the boundary.
- Adding the widget **breaks the "no APK rebuild" property** the WebView shell was designed for: widget changes ship only in a new APK. Keep logic here to a minimum for that reason, and prefer changing the web app.

## Web client deploy

Any push to `main` of the `RMoney-web` repo triggers `.github/workflows/deploy.yml` → GitHub Pages. The repo must stay public (GitHub Free doesn't serve Pages from private repos). No build step: `index.html` is served as-is, so all JS/CSS is inline there.

## Constraints from the owner

- No accounts/services beyond what exists (no Expo/EAS account, no app stores, no paid Apple Developer).
- No PIN/auth on the web app — considered and explicitly rejected.
- Dates in the sheet must render as Italian "d mmm yyyy" with no time component.
