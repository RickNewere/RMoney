## What this is

RMoney is a personal expense-entry app (two users: Riccardo and Roberta) that appends rows to a shared Google Spreadsheet (ID `10NT_nAkXRX12sEzFdpa6khSnONfjwm-NHGguoDm215U`). There are two sibling projects on the Desktop that share the same backend:

Also contains the backend source in `backend/Codice.gs`. **`App.js` is now a thin WebView shell** (`react-native-webview`) that loads the live web app (`SITE_URL = https://ricknewere.github.io/RMoney/`), so Android has full feature parity with the web (insert, debito, riepilogo, charts) and future web changes need no APK rebuild. The old native insert form was replaced, so `App.js` no longer imports `config.js`. - `C:\Users\rober\Desktop\RMoney-web` — static PWA (single `index.html`), deployed to GitHub Pages at https://ricknewere.github.io/RMoney/ (repo `RickNewere/RMoney`, public). This is the iPhone client (Add to Home Screen from Safari).

## Architecture

Backend = a Google Apps Script Web App bound to the spreadsheet (`backend/Codice.gs`). Clients talk to it over HTTPS:

- `GET  {API_URL}?action=categorie&gid=...` → `{ok, version, categorie:[...]}` — distinct values actually used in the CATEGORIA column of that tab, sorted.
- `POST {API_URL}` body `{gid, data:"YYYY-MM-DD", spesa, categoria, nota, segno}` → appends a row.
- `GET  {API_URL}?action=riep&conto=Euro|Franchi&tipo=annuale|mensile&anno=YYYY[&mese=M]` → `{ok, version, riepilogo:{...}}`. Read-only. Recomputes the summary from the two LOG sheets of the currency for an arbitrary period (a month or a full year), so the web "Riepilogo" section can pick any month/year. Same shape as `riepilogo` (overview/entrate/risparmio/spese per person + andamento for annuale). Classification mirrors the SOMMARIO sheets: a row is a **spesa** iff its category is one of the 15 in `SPESE_CATS`; everything else (stipendi, tredicesime/quattordicesime, and **storni e rimborsi**) counts as **entrata**; `risparmio = entrate - spese`. Validated against SOMMARIO ANNUALE 2025 (entrate exact; spese within ~7€ due to minor LOG-vs-sheet category quirks). This is what the web app uses now; the older `?action=riepilogo&gid=` (reads a fixed SOMMARIO sheet) is kept but unused.
- `GET  {API_URL}?action=riepilogo&gid=<gid di un foglio SOMMARIO>` → `{ok, version, riepilogo:{...}}`. Read-only. Reads a SOMMARIO sheet (ANNUALE/MENSILE × euro/CHF) and returns `overview` (entrate/uscite/totale + `periodo`), `entrate` and `risparmio` per person (roberta/riccardo/totale), and `spese.roberta`/`spese.riccardo` as `[{categoria, importo}]`. For ANNUALE sheets it also returns `andamento` (monthly savings series roberta/riccardo/totale) read from the hidden pivot sheet. The 4 SOMMARIO gids: annuale euro `738641296`, annuale CHF `637629592`, mensile euro `282752746`, mensile CHF `387921258`. Values come from `getValues()` (the accounting "-" is numeric 0); anchors ("OVERVIEW", "ENTRATE", "RISPARMIO", "SPESE ROBERTA/RICCARDO") are matched by text so the extraction survives row shifts.
- `GET  {API_URL}?action=debito&gid=X&gidPartner=Y` → `{ok, version, debito:{mio:{totale,meta,conteggio}, partner:{...}, netto}}`. Read-only. Sums the amounts of rows whose `split` cell is ticked (shared expenses split 50/50); `meta`=totale/2. `netto = mio.meta - partner.meta` is the per-currency settlement between the two same-currency tabs (>0 ⇒ partner person owes the tab's person). `gidPartner` is optional. This never writes to the sheet.
  - **This number is never cached anywhere, on purpose. Do not add a cache back.** v23 to v26 kept the total in `CacheService` for 30 minutes because the computation cost tens of seconds, and each client kept its own copy on top of that. The result was the worst possible failure for this particular feature: the same debt read three different values on three devices (iPhone 359,23 vs 360,23 in euro, Samsung 362,23 vs 360,23, and CHF 0,40 while the sheet had zero ticked rows). A shared debt that does not agree between the two people looking at it is worthless, and no amount of latency justifies it. The `onEdit` trigger added in v26 to invalidate that cache went with it.
  - What replaced the cache is **reading less**: `_totaleCondivise` now reads only the amount-to-split span (4 columns instead of 25 on LOG RICCARDO, so ~3.100 cells instead of ~19.500). If this ever gets slow again, narrow the read further or bound the rows. Do not store the result.
  - `?action=condivise` lists the same rows one by one and is the tool for checking the total by hand. It reads the full width, so it is the slower of the two; that is fine, it is a diagnostic.
- `GET {API_URL}?action=cerca&gid=X&importo=N&nota=S` → `{ok, version, trovata:bool}`, **v29**. Answers only "is this expense on the sheet?", by scanning the last 60 rows of the tail and just the amount-to-note span. It exists because a write whose response is lost has almost certainly succeeded, and the client must be able to tell **quickly** — it used to ask `?action=spese`, which recalculates a whole month across two sheets, i.e. the heaviest endpoint, at the exact moment the queue is already jammed, so the check itself often failed and the user got "non riesco a verificare" for an expense that was there. Measured on the real backend: **2,04 s** to confirm a write whose response had been lost. Sixty rows is enough because a new expense is inserted in date order and can never land above `SORT_FROM`.
- `GET {API_URL}?action=debiti` → `{ok, version, fogli:{"<gid>":{totale,meta,conteggio}, …}}` for all four LOG tabs, **v28**. It **throws if any of the four sheets cannot be read**, deliberately: returning zero for a missing sheet would show a confidently wrong debt, which is the one outcome this feature must never produce. This is what both clients use; `?action=debito` survives for the settle-verification path. The netto is two subtractions and is composed client-side.
  - **The point is the number of requests, not the payload.** Apps Script serialises requests from the same user, so an extra request is not merely slower, it queues behind the others while its own abort timer runs. Per-combination reads meant two requests for the widget and one per tab switch in the app; opening the app fired both sets at once and the euro read died twice with `Aborted` (seen in logcat) while francs went through. One request also opens the spreadsheet once for all four sheets instead of four times (`_ss()`/`_getSheetByGid` memoise within the execution).
  - Client consequence, and it is not a cache: the four totals come from **one read at one instant**, so switching person or account is instant and the four figures can never disagree with each other. Nothing is persisted; a reload re-reads.
  - **Apps Script serialises by the executing user, which is the owner** — not by caller. So requests from the phone, the widget, the iPhone and a terminal all queue behind one another, globally. Anything that fires an extra request makes every other client wait, which is why request count matters more here than it would against a normal API.

### The page feeds the widget (App.js)

Opening the app used to fire the same read twice at the same moment: the WebView page asked for the debt, and `aggiornaWidget('avvio')` asked for it too. They queued, and the widget's request was aborted twice in a row at 25 s (seen in logcat) while the page's went through. Making it one request per side did not fix it, because two sides were still asking.

Now `SPIA_SCRITTURE` (injected into the WebView) also watches **GET** responses: when it sees `action=debiti` come back it posts `debiti:<json>` to the native side, and `aggiornaConDati()` draws the widget from those totals without touching the network. On launch the widget only calls `disegnaDallaCache()` so it is never blank, and a 15 s timer (`ATTESA_DATI_PAGINA_MS`) does its own read **only if** the page never delivered. `foglio-cambiato` resets that flag, because after a write the page re-reads and will hand over the fresh numbers itself.

Two consequences to keep in mind when touching this: the spy must `res.clone()` before reading the body (the body can only be consumed once, and the real one belongs to the page), and it is coupled to the endpoint name — rename `action=debiti` and the widget silently falls back to reading it itself.

**The debt widget stores nothing.** `DebitoWidget:ultimo` in AsyncStorage is gone, on the owner's explicit instruction, and so is the two-pass "draw from cache, then redraw from the network" in `aggiornaOra`. `componiDebito()` is now a pure transform. Consequences that are intended, not bugs to fix: after a reboot or a reinstall the widget shows its empty "tocca per riprovare" state until a read succeeds, and a failed read leaves that state rather than an old figure. The reasoning is the owner's and it is sound — this number decides who pays, and a wrong one is worse than none. Note what removing it does **not** change: the launcher keeps displaying the last RemoteViews it was given until a new draw replaces them, so "the number on screen is the last one drawn" is a property of Android widgets, not of any cache. `widgets/riepilogoData.js` still caches the monthly donut; that is a different widget and a different number, and it was deliberately left alone.
- `GET  {API_URL}?action=condivise&gid=X` → `{ok, version, condivise:{tab, righe:[{riga, data, importo, categoria, nota, split}], totale, meta}}`. Read-only (v17). Itemises the rows the debt calculation sums, with their **sheet row number**, using exactly the same criteria as `_totaleCondivise`. This exists to reconcile the debt by hand: a mismatch is normally one forgotten row, and this turns "the total looks wrong" into "row 758, bennet, 12,51" in one call.
- `GET  {API_URL}?action=spese&conto=Euro|Franchi&tipo=annuale|mensile&anno=YYYY[&mese=M]&persona=Riccardo|Roberta|Insieme&categoria=<nome>` → `{ok, version, spese:{categoria, persona, valuta, periodo, righe:[{data, ts, importo, nota, persona, riga}], totale, conteggio}}`. Read-only (v18). The drill-down behind the web summary: `?action=riep` gives per-category totals, this gives the single expenses making up one of those totals, newest first. It filters the same LOG rows with the same period logic as `getRiepCalc`, so the sum of `righe` always matches the category total shown in the summary — if it ever doesn't, the two filters have drifted apart.
- Debug endpoints: `?action=debug&gid=` (tab name, row/col counts, first rows, last row) and `?action=catdebug&gid=`.

Tab routing: the four spreadsheet tabs are selected by Persona+Conto via gid — Riccardo Euro `113020932`, Roberta Euro `1888286288`, Riccardo Franchi `650699013`, Roberta Franchi `1063479927`. The map is duplicated in `config.js` (native) and in `RMoney-web/index.html` (web); change both.

Backend column handling (important — the sheets are not plain tables):

- Row 1 of each tab is a title; real headers are on row 2. `_findHeader()` scans the first 8 rows and scores keyword matches to find the header row. Never assume row 1.
- Columns are matched by substring on header names (`_colFor`): amount matches €/chf/importo/…, note matches dettagl/nota/…
- Date cell gets number format `d mmm yyyy` (renders "20 lug 2026" with the sheet's Italian locale) — no time.
- Shared expenses are marked in a dedicated **`split`** column (header `split`, real Sheets checkbox) placed immediately to the RIGHT of the note column. A row is shared if that cell is boolean `true` (or the legacy `-`, still recognized for backward compat). The boolean travels **inside the row's values**, but the cell must already carry checkbox validation when it is written — a bare `true` on a cell without it renders as the literal text "true" (this was a real bug). So `insertCheckboxes()` runs on the range about to be rewritten, immediately before the `setValues`; it also resets those cells to `false`, which is why the order cannot be swapped. If the `split` header is absent it falls back to writing `-` at note+1. `saldaFoglio` likewise re-applies `insertCheckboxes()` after clearing, so it never leaves the text "false" on cells lacking validation.
- **A written row does not inherit formatting** — it only gets what already exists in the destination row. The tabs carry an accounting currency format (` € 9,50 `, ` CHF 22,70 `) applied to a *finite* range, so once the data outgrows that range new rows are born unformatted and an amount shows as `1` instead of ` € 1,00 `. This actually happened on LOG RICCARDO at row 770 and is why inserts "stopped working" after months of being fine. `aggiungiSpesa` copies formats with `copyTo(..., PASTE_FORMAT)` and re-applies the date format, but **only when the write extends past the previous last row** — rows that already existed are already formatted, and since v25 that check saves two sheet operations on every insert that reuses space. The model row is the **first data row** (`h.row + 1`), deliberately not the row above: when the last rows are already broken, copying from them propagates the defect.
- `sistemaFormatoRighe(gid, daRiga, aRiga)` repairs rows written before that fix, by hand from the Apps Script editor. It writes **formatting and checkboxes only** and preserves existing ticks: dates, amounts, categories and notes are never touched. **The one real case (LOG RICCARDO, rows 770-774) is already sorted — the owner fixed it. Do not suggest running `sistemaRigheRotteRiccardoEuro()` again;** it is kept only as a template should the same breakage reappear elsewhere.
- One-time setup: `setupSplitColumn()` (run manually from the Apps Script editor) adds the `split` header + checkboxes to the 4 known tabs and converts existing `-` marks to checked. Touches only that single column.
- The spreadsheet has a **hidden sheet** "Tabelle brutte che nessuno vuole vedere" (gid `1943088578`, constant `GID_PIVOT`) holding the source pivots for the SOMMARIO charts, including the monthly "Andamento Risparmi" series (euro table first, CHF table second). `?action=riepilogo` reads the andamento from here.
### What actually costs time on a write

**Every mutation makes the whole spreadsheet recalculate** (the SOMMARIO tabs and the pivot read the LOG tabs), so the write cost tracks the **number** of sheet operations, not how much data is read. Reads are comparatively cheap.

v24 performed ten mutations per insert: write the row, copy the format, set the date format, insert the checkbox, set its value, sort the whole tail, remove every checkbox, clear the column, re-insert every checkbox, write the column back. v25 does **four** (copy format, date format, one `insertCheckboxes`, one `setValues`) and usually rewrites a single row. Delete went from six to two. **Do not reintroduce a per-write operation without measuring it** — this is the failure mode that made the app unusable, and it is invisible in the code because each individual call looks harmless.

Measured on v29, one real expense inserted and then deleted on each tab, **with a `?action=debiti` read deliberately left in flight** so the write finds the queue busy — that is the state the app is actually in, and measuring without it flatters the numbers:

| tab | insert, no tick | insert, shared tick |
|---|---|---|
| LOG RICCARDO (€) | 3,38 s (script 1954 ms) | 3,05 s (script 1417 ms) |
| LOG ROBERTA (€) | 3,01 s (script 1366 ms) | 2,56 s (script 1112 ms) |
| LOG RICCARDO CHF | 3,24 s (script 1672 ms) | 3,40 s (script 1861 ms) |
| LOG ROBERTA CHF | 3,47 s (script 2066 ms) | ceiling hit, see below |

Seven of eight land between 2,56 s and 3,47 s, and **the tick costs nothing** — the two cases differ by a couple of hundred milliseconds. The eighth ran while Google was stalling (the parallel read took 32,89 s), so the write sat in the queue past the client ceiling; the recovery path confirmed in 2,04 s that the expense was on the sheet. For comparison, v24 on LOG RICCARDO: 4,58 s without the tick and **29,00 s** with it, script execution alone.

**Inside the script the write is ~1 s in every case.** When a write feels slow it is never the writing itself — check the response's timings before touching `aggiungiSpesa`.

### Where a slow write actually goes (measured, don't re-derive this)

A `/exec` call has four parts. Since v31 the write response carries `ms` (the code), `msFlush` (the sheet flush, i.e. the recalculation) and `msTotale` (the whole execution); subtracting `msTotale` from the first HTTP leg gives the **dispatch** — the time Apps Script takes to *start* the execution, during which none of our code runs. Forty timed writes on LOG RICCARDO with the tick:

| part | typical | worst seen |
|---|---|---|
| dispatch (Apps Script starting the execution) | 0,8-1,9 s | **10,92 s** |
| our code (`ms`) | 0,9-2,5 s | 3,25 s |
| sheet flush / recalculation (`msFlush`) | 0,2-0,5 s | 1,04 s |
| retrieval leg (fetching the result) | 0,2-0,8 s | **41,82 s** |

Two independent failure sources, and both are Google's:
- **The retrieval leg** stalls for 12-42 s and then serves an error page. **The client no longer waits for it** (`apiPostSenzaRitorno` uses `redirect: 'manual'`), so this one is neutralised: the row is already written when Apps Script answers with the redirect.
- **Dispatch** spikes to 8-11 s on roughly 3 writes in 20. Nothing in the code influences it, and it does not correlate with the sheet, the tab, the tick, or concurrent requests. This is the entire remaining cause of a slow save.

Things that were suspected and **measured to be innocent** — do not chase them again: the workbook recalculation (0,2-0,5 s, despite ~270 SUMIF/SUMIFS over 1000-row ranges across six SOMMARIO tabs plus 144 pivot formulas — see `?action=formule`), the number of mutations, concurrent reads (a write completed in 4,65 s while a parallel read took 16,39 s), and Apps Script serialising executions (it does not: they overlap).

The only remaining lever is architectural: writing through the Sheets API directly instead of Apps Script, which removes the dispatch entirely at the cost of a Google sign-in per device. Proposed to the owner, awaiting a decision.

`aggiungiSpesa` returns `ms` and `passi` (per-step timings) in its JSON. Read those first when a write feels slow; they separate "the script is slow" from "Apps Script is queueing", which look identical from outside. Typical shape of `passi`: `foglio ~300, intestazioni ~350, lettura coda ~250, formato ~15, caselle ~180, scrittura ~270`. Roughly half of that is `openById` plus the header scan, i.e. fixed overhead before any work happens.

**Do not measure by firing requests back to back.** Apps Script serializes executions per user and Google throttles the retrieval leg: two POSTs in a row measured 1,1 s of script time but 9,9 s of HTTP. Leave 20-25 s between calls to measure what a person actually experiences.

- **Tail-only date ordering.** `SORT_FROM` maps each LOG gid to the first row the app is allowed to reorder, frozen on 27/07/2026 at that sheet's then-last row + 1 (Riccardo € 775, Roberta € 565, Riccardo CHF 105, Roberta CHF 106). Everything above the threshold is never read or moved: the history keeps whatever order it already had, which is **not** chronological (a sample of 122 rows had 9 date inversions), so the sheet as a whole will never become fully sorted — that was the accepted trade-off for not disturbing existing rows. Do not recompute these thresholds: raising them abandons rows already being sorted, lowering them reshuffles the frozen history.
  - **Since v25 nothing is sorted on write.** `aggiungiSpesa` reads the tail once, works out in memory where the row belongs by date, and rewrites only from the first row that actually changes. A same-day expense therefore touches exactly one row; a back-dated one shifts the few rows below it. Equal dates keep insertion order (the scan takes the first strictly-greater date), so the newest of a day sits last.
  - Holes left by deletes are dropped when that in-memory list is built, so the tail **compacts itself** on the next insert. That replaced `_primaRigaLibera` (reuse one blank) and the old "blanks sort to the bottom" trick, both gone.
  - `riordinaCoda(gid)` is the manual repair tool if a tail ever ends up genuinely out of order (a hand edit on the sheet). Run from the Apps Script editor. It sorts in memory and writes once, rather than `Range.sort()`.
  - **An emptied row must be left with NO checkbox (v21).** Up to v20 `svuotaRiga` kept an unchecked box on the cleared row, reasoning that reuse needed the validation in place. The owner rejected that: a grey box on a row with no expense reads as a leftover. It also had a concrete cost, since a boolean counts as content, so `getLastRow()` never shrank and the sheets over-reported their length (LOG RICCARDO said 777 rows against a real 774). Keeping the box was never actually necessary: `aggiungiSpesa` re-applies `insertCheckboxes()` over the range it is about to write.
  - `_sistemaCheckboxCoda()` survives only for `pulisciCheckboxVuote()`. It is no longer on any write path. Its two-pass shape is still load-bearing there: full rows get `insertCheckboxes()` and their boolean written back, empty ones get `removeCheckboxes()`, and the ticks must be read out **before** touching the column because `removeCheckboxes()` also wipes the value.
  - `pulisciCheckboxVuote()` is a one-off for the residue left by ≤v20 deletes: it runs `_sistemaCheckboxCoda` over the tail of all four sheets, then `_togliCodaVuota()`. Run once from the Apps Script editor — note that runs the **saved** code, so no redeploy is needed for it. Afterwards it has no further purpose, since a normal insert or delete cleans that sheet's tail anyway.
  - `_togliCodaVuota()` exists because not every stray checkbox came from a delete. `sistemaFormatoRighe` applies the box across a whole row range, blank rows included, so the manual repairs left blank-but-checkboxed rows **below** `SORT_FROM`, in the frozen zone the sorter never touches (confirmed on LOG RICCARDO row 774). It strips the box only from **trailing** blank rows and stops at the first row holding a real expense, so the history is never rewritten; it also bails if `getLastRow()` fails to shrink, which means some other column is keeping that row alive.
  - Consequence for clients: shifting rows invalidates the row numbers held by an open `?action=spese` list. The `atteso` guard on delete is what keeps that safe — it refuses rather than deleting whatever now sits at that row number.
- `POST {op:'elimina', gid, riga, atteso:{importo, nota, categoria}}` → `svuotaRiga()` (v19). Blanks date/amount/category/note on that ONE row with a single `setValues` over the span those columns occupy, rewriting any column in between with the value it already had, so formatting and neighbouring data survive; since v21 it removes the split checkbox entirely rather than leaving it unchecked. It no longer reorders the tail afterwards (v25) — the hole simply waits for the next insert to compact it. It deliberately **does not delete the row**: removing it would shift everything below and invalidate every row number already handed to the client by `?action=spese`. `atteso` is a guard, not decoration — the row is only cleared if it still holds the amount, note and category the user was looking at, so a stale list cannot wipe the wrong expense. Reachable in the UI only from the category detail view.
- `POST {op:'salda', gid}` → `saldaFoglio(gid)` unchecks every `split` cell of that ONE tab (write limited strictly to the split column; expenses are left intact). Backs the in-app "Saldato · azzera split" button, which confirms before firing.
- `POST {op:'annullaSalda', gid}` → `annullaSalda(gid)` puts back exactly the ticks the last settle removed (v22). **This exists because the settle used to be irreversible and 29 ticks were lost on LOG RICCARDO.** Since v22 `saldaFoglio` records the affected row numbers in `PropertiesService` before clearing; the undo re-ticks them and then **consumes** the record, deliberately — undoing twice, or much later, would re-tick rows that may have changed meanwhile. The web client shows an "↩ Annulla" button after a successful settle, and the confirm dialog now states the amount at stake instead of a generic "are you sure".
- **The undo is not retroactive.** Ticks cleared by a pre-v22 deployment left no record, so nothing can restore them from the script. For that case there is `ripristinaSplitDaCopia(idCopia [, nomeTab])`, run by hand from the editor: the owner makes a *copy* of an older revision via File → Cronologia versioni → three dots → "Crea una copia", and the function reads the `split` column out of that copy and re-applies it. It pairs sheets **by name** (a copy has its own gids), touches only the split column, and is **additive** — it never clears a tick, so expenses and ticks added since the copy survive. This is how the 29 rows were actually recovered; verified afterwards against the known figures (29 rows, 1068.67, net -362.23) with the August expenses still intact.

CORS: Apps Script `/exec` sends `Access-Control-Allow-Origin: *`. The web client POSTs with `Content-Type: text/plain;charset=utf-8` to avoid a preflight — don't change it to `application/json`.

## Backend deployment (manual, no CLI)

`backend/Codice.gs` is source only — it runs inside the sheet's Apps Script editor (Estensioni → Apps Script), where the user pastes it. To ship a change **without changing the URL**: Distribuisci → Gestisci distribuzioni → ✏️ → Nuova versione. A "Nuova distribuzione" creates a NEW `/exec` URL and breaks both clients (this happened repeatedly; the URL then has to be updated in `config.js` AND `RMoney-web/index.html`).

The `VERSION` constant in Codice.gs is a deliberate marker: bump it and check any endpoint's `version` field to verify what's actually live. Local Codice.gs is **v33** (`_ss()` uses `getActiveSpreadsheet()` — the script is bound to the sheet, so it does not need to look it up by id; the "foglio" step went from 236-1593 ms to 209-470 ms), earlier **v32** (`?action=cerca&totali=1` returns the debt with the write confirmation, so a shared insert costs two executions instead of three), **v31** (timings for dispatch/flush in the write response, plus the read-only `?action=formule` census), **v30** (`_totaleCondivise` reads each sheet **once**, headers and data in one block: five round trips for `?action=debiti` instead of nine, measured 3,0-3,4 s against 4-20 s before — and a shorter execution is also far less likely to have its response lost by Google's retrieval leg), earlier **v29** (`?action=cerca`, the cheap "is it on the sheet?" check), **v28** (`?action=debiti`: all four sheets in one request, spreadsheet opened once), **v27** (no debt cache at all, narrow column read instead), **v26** (a hand edit invalidated the debt cache; superseded), **v25** (one sheet operation per write; see "What actually costs time on a write"), **v24** and **v23** (the server-side debt cache, since removed), **v22** (the settle operation is reversible, plus `ripristinaSplitDaCopia`), **v21** (a deleted row leaves no checkbox behind), **v20** (tail-only date sorting + blank-row reuse), **v19** (`{op:'elimina'}`), **v18** (`?action=spese`, the per-category drill-down), **v16** (v15/v16: new rows copy their formatting from the **first data row** and always get a split checkbox, plus `sistemaFormatoRighe(gid, da, a)` to repair rows written before the fix; the formatting bug is closed — the fix is live and the affected rows have been repaired), earlier **v12** (v10: split cell gets a real checkbox via `insertCheckboxes()`+`setValue(true)` after `appendRow` instead of a bare `true` that rendered as text; v12: adds `action=riepilogo`); a redeploy is required for it to take effect. v7's only addition (serving `backend/App.html` on plain GET) was superseded by the GitHub Pages client; `backend/App.html` is dead code kept for reference.

Current live URL (answered **v24** before the v25 redeploy): `https://script.google.com/macros/s/AKfycbyS6FWBiSglQWJ_3ft0BAkeEcOCwSdgYKo5yZGvsMrXA25iDB1a7iiwDNt9sWbY4-oQ7Q/exec`. Check it with `?action=debug&gid=113020932` rather than trusting this line.

**A `/exec` request is two legs.** The first is the script running (`POST /exec` answers 302); the second is fetching the result from `script.googleusercontent.com`. Timing them separately is the only way to tell a slow script from a struggling Google: measured on v25, one insert ran in **2,13 s** while the retrieval took **31,50 s** and then returned an HTTP **404 HTML page in German** — and the row was on the sheet. This is not hypothetical and it is not the script: it was reproduced repeatedly, and every time the expense had been written. It is what surfaces in the app as "risposta non valida, controllo il foglio…", and it is exactly why the client verifies on the sheet instead of resending. Never "fix" a lost response by retrying a write.

**A new URL means editing THREE files, not two:** `RMoney-web/index.html` (the `API` constant), `RMoney-web/api.json` (read at runtime by the Android widget), and `config.js`. Miss `api.json` and the app works while the widget silently keeps talking to the archived deployment.

At least five older deployments are still live and answering (v17 `AKfycbzH9jpm…`, v18 `AKfycbyT4YZ…`, v19 `AKfycbyVsbG2…`, v20 `AKfycbw4Bsnd…`, v21 `AKfycbzXHWg…`); they should be archived. Every one was created by choosing "Nuova distribuzione" instead of "Nuova versione", and the symptom was always the same: the code looks deployed but the clients keep talking to the old URL.

**Apps Script is the capacity bottleneck, and it degrades before it fails.** Measured under load on the free tier: the same `?action=categorie` call took 2.7 s, then 19.6 s, then 33.5 s, the last two returning an **HTML page instead of JSON** with HTTP 200. Two minutes of quiet and it was back to 6.9 s and correct data. So it is congestion, not an exhausted daily quota, and the client's job is to ask less and to survive a non-JSON answer rather than to retry harder. Every widget refresh costs three requests, which is why the refresh cadence is deliberately conservative (see the widget section).

Icons are generated by `backend/make_icon.py` (Pillow) → writes `assets/icon.png`, `adaptive-icon.png`, `splash.png`, `favicon.png`. The icon is "RM" with a green (#22c55e) € badge; regenerate with the script rather than editing images.

There is no test runner. Renderer/widget files are checked by transpiling them with the project's own Babel before building, which catches syntax and JSX errors in seconds instead of after a 2-minute Gradle run:

```powershell
node -e "const b=require('@babel/core'),f=require('fs');for(const x of ['App.js','index.js','widgets/aggiorna.js']){b.transformSync(f.readFileSync(x,'utf8'),{filename:x,presets:['babel-preset-expo'],babelrc:false,configFile:false});console.log(x,'OK')}"
```

**Do not use `npx babel` for this.** It is not installed, so npx silently fetches `babel@5.8.38` (the 2015 package), which "succeeds" on anything and reports OK for files that do not compile. Pure functions (`formattaImporto`, the throttle logic, the coalescing guard) are tested the same way the sibling projects do it: copy the function into a `node -e` script with a table of cases and count matches.

Known pitfalls:
- `babel-preset-expo` must stay pinned `~54.0.10` to match Expo SDK 54 — a newer major breaks the build.
- `npx expo export` fails on Windows (hermesc.exe "private properties are not supported") — known Windows-only bug; it does NOT affect `expo start` or the Gradle build. Validate bundles via the dev server instead.
- After reinstalling the APK, Android launcher may cache the old icon (uninstall + reboot fixes it).

## Android home screen widget

Two widgets: **"Debito"** (2x2, shared balance per currency) and **"Riepilogo"** (full width, the same balance plus a donut of the month's income/spending/savings). They are the one part of the Android app that is NOT the WebView, and that is not a choice: an Android widget is drawn by the launcher process from `RemoteViews`, so it cannot host a WebView or run the web app. Built with `react-native-android-widget` (v0.21, Expo config plugin). Expo's own `expo-widgets` is iOS only, which is also why the iPhone client, being a home screen web app, can never have one.

Files, and which layer each belongs to:

| file | role |
|---|---|
| `index.js` | entry point: registers the app, the widget task handler and (by importing it) the periodic task |
| `App.js` | WebView shell + the write-spy injection + the refresh triggers |
| `widgets/aggiorna.js` | the only place that calls `requestWidgetUpdate`; throttling, coalescing, two-phase draw |
| `widgets/attivitaPeriodica.js` | the WorkManager periodic job |
| `widgets/disegna.js` | composes either widget; single source of truth for the trees |
| `widgets/debitoData.js` | debt fetch, retries, cache, `formattaImporto` |
| `widgets/riepilogoData.js` | monthly summary fetch (**francs**, see below) |
| `widgets/tortaSvg.js` | donut geometry as an SVG string for `SvgWidget` |
| `widgetTaskHandler.js` | headless dispatch for system-initiated updates |

- **The donut reads the FRANCS sheet, and that is deliberate.** Salaries land on the CHF account, so the euro sheet has `entrate: 0` in every month and a euro donut would forever read "all spending, negative savings". July francs: income 8720.60, spending 1881.53, savings 6839.07. Two slices, not three: savings is already income minus spending, so a third slice would count income twice — the ring *is* the income. If income is 0 or spending exceeds it there is no share to draw, and the ring goes solid red instead of inventing a proportion. If the current month has no movements yet (typical on the 1st) it falls back to the previous month, and the label always names the month shown.

- **`package.json` `main` is `index.js`, not `expo/AppEntry.js`.** The widget handler has to be registered next to `registerRootComponent`, and the default Expo entry point only does the latter. Reverting `main` silently disables the widget: the app still runs, the widget just never draws.
- The widget declaration lives in `app.json` under `plugins`. `expo prebuild` turns it into `android/app/src/main/res/xml/widgetprovider_debito.xml`, a `<receiver android:name=".widget.Debito">` in the manifest, and a generated `widget/Debito.java` extending `RNWidgetProvider`. All of that is regenerated, so never hand-edit it — change `app.json` and prebuild.
- **The backend URL is resolved at runtime** from `https://ricknewere.github.io/RMoney/api.json`, with `config.js`'s `API_URL` as fallback. This exists because the Apps Script URL changes on every "Nuova distribuzione" (five times in a single day of work at one point) and a URL compiled into the APK would leave the widget dead until someone rebuilt it. That JSON file lives in the `RMoney-web` repo and has to be updated together with `index.html`.
- `leggiDebito()` never rejects. On any failure it falls back to the last value cached in AsyncStorage, flagged `vecchio`, because a widget showing a stale number beats one showing nothing. If there is no cache either it returns empty and the widget invites a tap.
- **Never let two backend reads overlap, and never parallelise them.** This cost hours. Apps Script serialises requests from the same user, so concurrent calls do not run concurrently: the second one sits in a queue while its own abort timer runs, and dies with `Aborted`. A `Promise.all` over the two currencies (written as an "optimisation") made the second currency fail on every attempt, and because one failure discarded the whole result the widget silently kept redrawing the same stale numbers for hours. Measured on the live backend: euro ~3 s, francs ~10 s alone, **16 s when fired together**. Two rules follow, both enforced in code: the currencies are read **one after the other**, and `leggiDebito()`/`aggiornaWidget()` each keep a single in-flight promise so that the five triggers (app start, app exit, periodic job, widget tap, the wide widget wanting the same data) share one read instead of racing. Verified: with the guard, three simultaneous callers produce exactly one real execution.
- **`TIMEOUT_MS` must stay well above the slowest single call.** It was 12 s while the francs call alone takes ~10 s — a fuse waiting to blow even without the parallelism bug. Now 25 s with 2 attempts.
- **A failure on one currency must not discard the other.** It used to, which is why a fresh euro figure was thrown away because francs had timed out. Each currency now falls back to its own cached value.
- **`requestWidgetUpdate` resolving means nothing.** The library resolves as soon as it has *launched* the draws — internally a `forEach` with an async callback — so a failure inside becomes an unhandled rejection and vanishes. The app logged "widget aggiornato" for hours while the widget on the home screen never changed. Any log that claims success must come from **inside** `renderWidget` (see the `disegno` / `disegno pronto` / `disegno FALLITO` traces), never from the outer promise. When debugging this widget, the only trustworthy evidence is the clock drawn in its own corner.
- **`updatePeriodMillis` is not the periodic refresh; WorkManager is.** The widget alarm fires (`dumpsys alarm` showed it at 18:54, 19:29, 19:43) while the widget stayed frozen for eight hours, which matches the API contract: best effort, the device is never woken for it, OEM power management delays it further. The real periodic refresh is `expo-background-task` (WorkManager) in `widgets/attivitaPeriodica.js`, at **30 minutes**. It is the only mechanism that can pick up an expense entered from the *other* person's phone, because Apps Script cannot push to a device.
- **The battery exemption is what actually makes the periodic job run**, and it is the first thing to check when "the widget never refreshes on its own". Without it JobScheduler showed the job overdue by 16 minutes, all constraints satisfied, `Active jobs: N/A` — scheduled and simply never executed, with `!restricted=false` in the `Ready:` line. Granting it flipped that to `!restricted=true` and the worker started firing. It cannot be granted silently (that needs `WRITE_SECURE_SETTINGS`), so `widgets/esenzioneBatteria.js` opens the system dialog pointed at this package, once, four seconds after launch; the permission `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is declared in `app.json`. Check the current state with `adb shell dumpsys deviceidle whitelist | grep rmoney`.
- **A concurrency guard must be able to expire.** `aggiornaWidget` keeps one in-flight promise; when an update hung and never settled, `inCorso` stayed set and **every** later update was discarded — the log read `aggiornamento gia' in corso, salto: lavoro periodico` while the widget sat frozen for hours. The guard now abandons an update older than `SCADENZA_CORSO_MS` (2 min) and starts a new one, only the current promise clears the slot, and `aggiornaOra` catches its own errors so it always settles. This is the shape of the worst bug in this file's history: a protection that, on its own failure, permanently disables what it protects. Verified end to end afterwards — a change made from another device reached the widget with the app never opened (361,23 → 362,23 at 16:30).
- **Never call `registerTaskAsync` unconditionally at startup.** Re-registering a live periodic job REPLACES it and restarts its countdown from zero. The call sat in an app-start effect, and since the owner opened the app precisely to check whether the widget had refreshed, every check pushed the next run 30 minutes away — it could never fire. Guarded now with `TaskManager.isTaskRegisteredAsync`; the log says `lavoro periodico gia' attivo, non lo tocco` on later launches, and that line is the proof the timer was left alone.
- **Refresh triggers, and the throttle between them.** `App.js` injects a script that wraps `window.fetch` in the WebView and posts `foglio-cambiato` on any successful POST to `/exec` — so adding, deleting and settling all refresh the widget within seconds. Plus app start, app exit, and the periodic job. `DISTANZA_MIN_MS` (10 min) suppresses *spontaneous* repeats, because opening and closing the app fired two reads seconds apart and that alone was enough to congest Apps Script. `SEMPRE` lists the reasons that bypass it: a sheet write, a widget tap, and **app start** — opening the app is a deliberate gesture, and throttling it made the widget stale exactly when it was being looked at.
- **Draw from cache first, then from the network.** After every reinstall Android resets the widget to its blank initial layout; with the backend taking 10-30 s the read rarely finished before the app went to background, so the widget stayed empty. `aggiornaOra` now draws immediately from the AsyncStorage cache and redraws when fresh data lands. The log distinguishes the passes as `(motivo/cache)` and `(motivo/rete)`.
- **Limit worth stating plainly:** the write-spy only catches changes made on *this* phone. A change made from the iPhone cannot arrive before the periodic refresh, a tap, or an app open.
- **Reinstalling the APK removes the widget from the home screen.** Observed, not theorised: `dumpsys appwidget` logged a `cancel` of the provider seconds after `adb install -r`, and the placed instance was gone. The provider itself re-registers fine, so the fix is simply to add the widget again by hand. Expect this after every rebuild and warn the owner rather than debugging a "widget disappeared" report. `dumpsys appwidget | grep -A2 rmoney` shows both the registered provider and the live instances, and its `min=(WxH)` is width and height in dp packed as `dp*256+1`, so 200x80dp reads as `51201x20481`.
- **Amounts are formatted by hand, and the rule is not the obvious one.** Italian CLDR sets `minimumGroupingDigits=2`, so `toLocaleString('it-IT')` prints `1165,86` with no separator and only starts grouping at `10.000,00`. The widget cannot call `toLocaleString` (headless task, full Intl not guaranteed), so `formattaImporto` reproduces that rule with an explicit `length >= 5` check. A "nicer" formatter that groups from 1.000 was written first and made the same number read differently in the widget and in the app. Verified: both agree on 13 values across the boundary.
- Adding the widget **breaks the "no APK rebuild" property** the WebView shell was designed for: widget changes ship only in a new APK. Keep logic here to a minimum for that reason, and prefer changing the web app.

## Web client deploy

Any push to `main` of the `RMoney-web` repo triggers `.github/workflows/deploy.yml` → GitHub Pages. The repo must stay public (GitHub Free doesn't serve Pages from private repos). No build step: `index.html` is served as-is, so all JS/CSS is inline there.
